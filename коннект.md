# Коннект: аудитор `mcp_audit` ↔ стенд Damn Vulnerable AI Agent

Документ о соединении двух независимых кодовых баз в ветке `new-stand`:

| Что | Откуда | Версия / коммит | Куда легло |
|---|---|---|---|
| Аудитор агентных систем | `bulochka68/aith_redteaming` | движок 2.0.0, схема отчёта `agent-security-audit` 2.0 | `mcp_audit/`, `profiles/`, `schemas/`, `examples/`, `docs/`, `tests/` |
| Стенд Damn Vulnerable AI Agent (DVAA) | [`opena2a-org/damn-vulnerable-ai-agent`](https://github.com/opena2a-org/damn-vulnerable-ai-agent) | 0.9.3, коммит `faf3fb172ef526d12db0eb5377701549693118a6`, Apache-2.0 | `stand/` (вкопирован целиком, без `.git`) |
| Связка | написано здесь | — | `profiles/dvaa.json`, `examples/dvaa.*`, `scripts/capture_dvaa_inventory.py`, `tests/test_dvaa_profile.py` |

Прежний стенд (GenAI Investment Assistant) и red-team харнесс из ветки убраны.
От старого стенда остались только **данные аудита** — профиль
`profiles/genai_invest_stand.json`, снимки и эталонные отчёты в `examples/`,
фикстуры в `tests/fixtures/stand/`; они ни на что в новом стенде не влияют и
нужны как регрессия движка.

## TL;DR — что получилось

Аудитор работает на системе, для которой он не писался: другой язык (Node.js
вместо Python), другие протоколы (MCP по HTTP + A2A вместо MCP по stdio),
другая модель памяти. Правила и движок при этом не менялись — вся привязка
уместилась в один профиль.

**Итог прогона:** 24 подтверждённые находки, 15 правил FAIL, 3 PASS (4 с базовой линией), покрытие
обязательных контролей 18/26 (69%). Полный отчёт — `examples/dvaa.report.md`,
машинный — `examples/dvaa.audit.json`.

**Главное ограничение:** все 24 находки — `static_supported`. Runtime-подтверждений
нет вообще, потому что живые режимы аудитора об этот стенд ломаются (см. проблему
№1) и трассы в него не заведены (проблема №6).

## 1. Как развернуть стенд

Нужен Node.js ≥ 18 (проверено на 22) **или** Docker. Стенд поднимает 21 агента на
портах 7001-7023 и дашборд на 9000.

```bash
cd stand
npm install                 # 110 пакетов, ~5 c
OPENA2A_TELEMETRY=off node src/index.js
# либо: node src/index.js --offline   (тот же эффект, плюс airplane-mode сервера)
```

Через Docker (собирается из `stand/Dockerfile`, тот же набор портов):

```bash
cd stand
docker compose up          # дашборд на http://localhost:9000
```

Проверка, что стенд живой:

```bash
curl -s http://localhost:9000/stats
curl -s http://localhost:7010/info
curl -s -X POST http://localhost:7010/ -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

Что важно знать до запуска:

- **Телеметрия включена по умолчанию.** `src/index.js` вызывает `tele.init()` и
  шлёт анонимную статистику наружу. Для аудита и закрытого контура запускайте с
  `OPENA2A_TELEMETRY=off` или флагом `--offline` — переменная читается **до**
  `tele.init()`, задавать её позже поздно.
- **Стенд намеренно уязвим и исполняет то, что ему говорят**: `execute` запускает
  команды, `read_file` читает файлы, `fetch_url` ходит по SSRF-адресам. Только
  локально, никогда наружу.
- **Конфликт портов** решается `HOST_PORT_OFFSET=<N>` (сдвигает порты, которые
  показывает дашборд); тот же сдвиг передаётся скрипту съёма инвентаря флагом
  `--port-offset`.

## 2. Как подключить аудитор

```bash
# 0) стенд поднят (см. выше). Аудитору нужен только Python 3.11+;
#    PyYAML — чтобы прочитать stand/docker-compose.yml
pip install -r requirements.txt

# 1) снять инвентарь MCP-агентов с живого стенда
python3 scripts/capture_dvaa_inventory.py -o examples
#    -> examples/dvaa.config.json           (клиентский MCP-конфиг + x_audit)
#    -> examples/dvaa.tools.snapshot.json   (снимок tools/list со временем и идентичностью)

# 2) прогнать аудит (offline: ничего не запускается, никуда не ходит)
mkdir -p .audit
python3 -m mcp_audit audit examples/dvaa.manifest.json \
  --json .audit/dvaa.json --md .audit/dvaa.md --gate

# 3) базовая линия определений — без неё TOOL-01 не оценивается
python3 -m mcp_audit baseline examples/dvaa.manifest.json -o .audit/dvaa.baseline.json
python3 -m mcp_audit audit examples/dvaa.manifest.json \
  --baseline .audit/dvaa.baseline.json --json .audit/dvaa.json --gate

# 4) регрессия связки в тестах
python3 -m pytest tests/test_dvaa_profile.py -q
```

Что с чем связано:

```
stand/src/*.js ──────────────┐
stand/docker-compose.yml ────┤
examples/dvaa.config.json ───┼──> examples/dvaa.manifest.json ──> mcp_audit ──> отчёт
examples/dvaa.tools.snapshot.json                                      ▲
examples/dvaa.policy.json ───┘                    profiles/dvaa.json ──┘
```

- `profiles/dvaa.json` — вся привязка к стенду: компоненты, типы памяти, потоки,
  переходы авторизации, цепочки. Правила его не знают, они работают с фактами.
- `examples/dvaa.policy.json` — **ожидаемая** политика: как выглядела бы та же
  система, построенная безопасно. Находки — это расхождение стенда с ней.
- `examples/dvaa.manifest.json` — что с чем связано в одном прогоне.

## 3. Проблемы соединения

### 3.1. У стенда нет `initialize` — живой режим аудитора не работает

MCP-агенты DVAA (`stand/src/index.js:1407`) реализуют ровно два метода:
`tools/list` и `tools/call`. Всё остальное — `-32601`:

```
$ curl -s -X POST localhost:7010/ -d '{"jsonrpc":"2.0","id":1,"method":"initialize", ...}'
{"jsonrpc":"2.0","id":1,"error":{"code":-32601,"message":"Method not found: initialize"}}
```

Аудитор начинает хендшейк именно с `initialize`
(`mcp_audit/discovery/introspector.py:329`), поэтому `--mode live-inventory` даёт
по всем четырём серверам:

```
toolbot | tools: 0 | handshake: ok=false, error="MCPError: Method not found: initialize", completeness=unavailable
```

Это **корректное поведение аудитора** (INV-02 требует, чтобы отказ discovery был
виден как `unavailable`, и конфиг не подменял успешный хендшейк), но полезного
инвентаря живой режим не даёт.

**Как обошли:** `scripts/capture_dvaa_inventory.py` сам вызывает `tools/list` и
сохраняет результат как *снимок* — со временем съёма, идентичностью и указанием,
что `initialize` не выполнялся. Манифест привязывает его при `live: false`, поэтому
снимок остаётся снимком: `INV-02` = PASS честно, а не потому что мы выдали конфиг
за хендшейк.

**Как закрыть по-настоящему** (на выбор):
- поправить стенд — добавить `initialize` и `notifications/initialized` в тот же
  `switch` в `stand/src/index.js` (десяток строк, ломать нечего);
- либо дать интроспектору аудитора флаг «продолжать при `-32601` на `initialize`»
  и помечать такой инвентарь как `completeness=partial` с явной причиной.
  Второе трогает движок и требует, чтобы деградация была видна в отчёте, — иначе
  разрушается смысл INV-02.

### 3.2. Стенд на JavaScript, статанализ аудитора — на Python `ast`

`mcp_audit/adapters/source_snapshot.py:102` строит AST только для `.py`; для всех
остальных файлов дерево пустое. Последствия:

| Что | Как это выглядит на JS |
|---|---|
| Поиск символа (`symbol: "Class.method"`) | не работает: символ не найден → поток `unknown` |
| `tool_declarations` (декораторы) | пусто: инвентарь «из исходников» для JS не строится |
| Проверка потока по `patterns` | **работает**: если `symbol` не задан, регулярки применяются ко всему файлу |
| Локатор в evidence | файл целиком (`lines: [1, 2231]`), а не строки нужного места |
| `fragment` в evidence | первые 600 байт файла — шапка и импорты, а не код, о котором утверждение |

Поэтому в `profiles/dvaa.json` ни у одного потока нет `symbol` — только `path` +
`patterns`. Это работает, но доказательная сила ниже: рецензент видит «в файле есть
такая строка», а не «вот эта функция».

Побочные эффекты:
- **INV-01 = INCONCLUSIVE**: сверять `configured` / `live_advertised` / `snapshot`
  есть с чем, а `source_defined` для JS взять неоткуда.
- **TOOL-01 = NOT_EVALUATED** без базовой линии: определения не с чем сравнивать
  (лечится шагом 3 из раздела 2).

Отдельная ловушка: раз `symbol` не задан, `negate_patterns` тоже применяются ко
**всему файлу**. Общее слово вроде `subject` найдётся где угодно и превратит
поток в `contradicted` — негативные шаблоны должны быть узкими (`req\.headers\.authorization`,
`setInterval`, `verifySignature`).

### 3.3. У стенда нет аутентификации, а AUTH-04 при `scheme: "none"` даёт PASS

`AUTH_SCHEME_REQUIREMENTS["none"] == []` (`mcp_audit/identity/model.py:23`), значит
проверок не требуется, значит пропусков нет, значит PASS. Формально верно — «токенов
нет, проверять нечего», — но в отчёте это читается как «с проверкой токенов
порядок» рядом с CRITICAL по AUTH-01.

**Как обошли:** в профиле у `token_validation` схема не указана вовсе, и правило
берёт её из ожидаемой политики (`mcp-tools: api_key`). Тогда оцениваются реальные
требования (`lookup`, `revocation`, `binding_to_principal`), ни одно не выполняется,
и получается честный FAIL: `mcp-tools: token validation skips lookup, revocation,
binding_to_principal`.

**Вывод для движка:** `scheme: none` стоит трактовать как INCONCLUSIVE с пометкой
«схема аутентификации отсутствует — см. AUTH-01», а не как PASS.

### 3.4. Один контейнер на 21 порт — инфраструктурные правила почти немы

`stand/docker-compose.yml` — один сервис `dvaa` с 21 опубликованным портом. Compose
читается (сервис в снимке деплоя есть), но:

- **INFRA-02 = NOT_EVALUATED**: правило ищет сервисы-хранилища, а их нет — вся
  память живёт в процессе. Публикация двадцати одного порта на хост при этом никак
  не оценивается, хотя для боевой системы это ровно то, о чём INFRA-02.
- **INFRA-01 = FAIL** получается только через объявленный в профиле поток
  `store_access` (`agent-fleet` держит `read+write+publish` на общей памяти при
  политике `read`), а не из деплоя.

Это ограничение постановки: у стенда нет отдельного хранилища, и сетевую границу
не из чего вывести.

### 3.5. Другая модель памяти

У стенда память — это `const memoryStore = {}` в процессе (`stand/src/index.js:230`),
ключ — `agent.id`. Нет ни владельца, ни сессии, ни аудитории, ни TTL, ни ревью —
то есть нет ничего, из чего аудитор обычно строит суждение.

Решение: в профиле объявлены **типы памяти как контракт** (`session_memory`,
`agent_rule`, `preloaded_secret`) с той аудиторией и авторитетом, которые
подразумеваются поведением стенда, а в политике — то, чего от них ждут. Аудитор
оценивает расхождение. Именно так и получены MEM-01…MEM-07, MEM-10.

Тонкость: `to`-узел потока `store_access` (`memoryStore:agent_rule`) обязан
совпадать с ключом в `service_rights` политики, иначе правило скажет «нет ожидаемых
прав» и уйдёт в INCONCLUSIVE. Имена компонентов профиля — это узлы графа; цепочки
(`chains`) собираются только по объявленным потокам, опечатка в имени = пустая цепочка.

### 3.6. Runtime-подтверждений нет: трассы стенда не заведены в аудитор

Все 24 находки — `static_supported`. Стенд при этом **пишет** наблюдения: журнал
атак дашборда (`:9000`), `sandbox.cmdLog` (выполненные команды), `sandbox.exfilLog`
(попытки эксфильтрации), статистика по агентам. Аудитор умеет их принимать —
адаптеры `trace` и `memory_event_snapshot`, режим `trace-review`, — но формат
DVAA в них не переложен.

Это самый дешёвый следующий шаг: конвертер `attack log → trace` поднимет
MEM-08/MEM-09/AUTH-06 из `NOT_EVALUATED` и переведёт часть находок из
`static_supported` в `runtime_supported`.

### 3.7. Организационное

- **Лицензии.** DVAA — Apache-2.0, вкопирован целиком с `LICENSE`; текст лицензии
  и авторство upstream не трогали. Аудитор — код этого репозитория.
- **Вложенный `.gitignore`.** `stand/.gitignore` продолжает действовать в
  подкаталоге: `node_modules/`, `.dvaa/`, `.hackmyagent-cache/` в репозиторий не
  попадают. `npm install` делается локально.
- **Вложенные workflow.** `stand/.github/workflows/` в подкаталоге GitHub Actions
  не выполняет — CI upstream не запустится в этом репозитории.
- **Обновление стенда.** `stand/` — снимок upstream на коммите `faf3fb1`. Обновление
  = перекопировать дерево и перечитать `profiles/dvaa.json`: привязка держится на
  регулярках по исходникам, они переживают правки кода не всегда.
- **Пересечение инструментов.** DVAA приносит с собой сканер HackMyAgent (`dvaa scan`,
  `.hackmyagent-cache/`). Он ищет уязвимые паттерны в сценариях стенда; наш аудитор
  строит отчёт из утверждений с источником, методом и статусом подтверждения. Задачи
  разные, конфликта нет, но результаты не взаимозаменяемы — не путать при сравнении.

`register_tool`, `store_secret`, `transfer_funds`, которых нет в
`authorized_tools` политики) — их аудитор нашёл сам, без описания в профиле.

## 5. Порядок работ, если продолжать

1. Конвертер журналов стенда в формат адаптера `trace` — самый большой прирост
   покрытия (3.6).
2. `initialize` в стенде **или** мягкая деградация в интроспекторе — включает
   живой режим (3.1).
3. `scheme: none → INCONCLUSIVE` в AUTH-04 (3.3).
4. Локаторы для не-Python исходников: хотя бы номер строки первого совпадения
   шаблона вместо диапазона всего файла (3.2) — дешевле полноценного JS-парсера и
   закрывает основную претензию к доказательности.
