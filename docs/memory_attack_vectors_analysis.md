# Атаки на память агента: анализ смежных решений и вектора расширения

> Аналитический отчёт. Разбирает три независимых red-team харнесса против того
> же класса целей, что и `memrot` (LLM-агент с долговременной памятью,
> инвестиционный стенд), и выводит из них список векторов, которыми мы могли бы
> расширить атаку на память — с привязкой к таксономии `memrot`
> (`memrot/taxonomy.py`, OWASP ASI06 / MITRE ATLAS).
>
> Область применения — **только авторизованное тестирование**. Ниже описаны
> механики техник и то, как их реализовали в коде смежные проекты; дословные
> боевые payload'ы намеренно не приводятся.

---

## 1. Что изучено

| Проект | Пакет / CLI | Уровень доступа к цели | Чем берёт |
|---|---|---|---|
| **Talent-Hub / MOROK** | `agentic_redteam` | white/grey-box (evidence из БД, логов, трасс стенда) | вердикт **только из состояния**; профиль как единственное место target-специфики; фикс-сценарий **и** автономный атакующий |
| **agentic-red-teaming / memnotsafe** | `memnotsafe` | mock (офлайн-канон) + live-адаптер | самый широкий каталог **семейств атак** (17 модулей); композитные oracle'ы; MITRE ATLAS / OWASP ASI, SARIF |
| **catfr0g / red-alert** | `red_alert` | black-box (только публичный HTTP API) | адаптивный планировщик-LLM; мультимодальные и кодировочные каналы доставки; Langfuse-трассировка |

Общая для всех троих модель угрозы совпадает с premise `memrot`: атака
считается успешной не по тексту ответа одного хода, а по тому, что **payload
пережил сессию и сработал позже — в другой сессии, у другого принципала, через
вызов инструмента**.

```
вход → контекст → память → планирование → выбор инструмента →
аргументы → результат → изменение состояния → следующая сессия
                         ▲ здесь атака уже победила, а ответ ещё «нормальный»
```

## 2. Как они применяли технологии (что стоит перенять)

### 2.1 Вердикт из состояния, а не из текста (MOROK)

Центральная инженерная идея MOROK — предикаты считаются по **наблюдаемому
состоянию цели**, а не по строке ответа. Реализовано разделением каналов:

- `evidence/` — провайдеры факта: `db_query`, `log_regex`, `http_canary`,
  `trace`, `state_reset`, `bundle`;
- `normalize/` — `Observation → Facts` (в т.ч. `memdiff` — дифф снимка памяти);
- `assertions/` — предикаты (`tool_principal_mismatch`, `cross_session_effect`,
  `memory_write`, `response_contains`) → вердикт.

Ключевой инвариант: текстовый предикат (`response_contains`) имеет **потолок
`indirect`** — «модель проговорилась» никогда не считается полным обходом
контроля. Это ровно словарь `memrot`: `CONFIRMED / CLEAN / ERROR / INVALID /
NOT_EVALUATED` и цепочка `path_state`
(`static_path_supported → runtime_path_observed → control_violation_observed`).

**Перенос в memrot:** мы уже имеем `detectors/ground_truth.py`. Стоит довести
до уровня MOROK различие «утечка в текст (indirect)» vs «реальный
cross-principal вызов (confirmed)» как **разные детекторы на одном прогоне**,
чтобы один и тот же payload давал две независимые метрики.

### 2.2 Многошаговая атака как одна попытка (MOROK, memnotsafe)

Оба проекта исполняют цепочку **внедрение → фиксация памяти → активация другой
ролью** как *одну* attempt: один сброс цели (`state_reset`), отдельное окно
evidence, собственный principal на каждый шаг. memnotsafe формализует это как
конвейер стадий:

```
scenario → baseline → attacker session → memory write →
новая victim-сессия → retrieval → tool-эффект → oracles → report
```

**Перенос:** в `memrot/runner` закрепить понятие «attempt = набор ходов с
разными принципалами + одно окно проверки», чтобы cross-session вектора
считались честно (сейчас акцент на матрице вариант×цель).

### 2.3 Композитные и специализированные oracle'ы (memnotsafe)

`oracles/` разнесён по слоям эффекта, и это готовая карта того, «что вообще
можно измерить» на памяти:

| Oracle | Что фиксирует |
|---|---|
| `persistence` | payload пережил конец сессии |
| `retrieval` | payload реально всплыл (retrieval сработал) в новой сессии |
| `adoption` | агент **принял** внедрённое как своё правило/факт |
| `memory` | факт записи/дифф памяти |
| `tool` | внедрённое повлияло на выбор/аргументы инструмента |
| `external_effect` | наступило реальное внешнее последствие (утечка/действие) |
| `composite` / `judge_merge` | склейка нескольких сигналов + LLM-судья |

**Перенос:** это лестница строгости, которой у `memrot` пока нет явно. Стоит
ввести шкалу `persist < retrieve < adopt < tool-effect < external-effect` и
маркировать каждый CONFIRMED уровнем, на котором он подтверждён.

### 2.4 Два режима генерации: фикс-сценарий и автономный атакующий (MOROK, red-alert)

- **Фикс-сценарий (YAML)** — воспроизводимость и регрессия.
- **Автономный атакующий-LLM** — разведка боем: сам выбирает сообщения,
  сессии, порядок; при слабом сигнале переформулирует.

red-alert строит это на LangGraph (`planner → target → judge`), с
переформулировкой при слабом extract. MOROK — `AttackBrief` (только задание +
критерий успеха) + binary judge поверх тех же state-evidence.

**Перенос:** у `memrot` есть `--adaptive` (PAIR/TAP-lite) и мутации. Логичный
шаг — «brief-режим», где фиксируется только цель и предикат, а порядок ходов и
выбор сессий отдаёт адаптивному атакующему.

### 2.5 A/B `vulnerable` vs `protected` (MOROK, memnotsafe)

Один и тот же сценарий гоняется в уязвимом и защищённом режимах стенда.
`vulnerable` → `proven`, `protected` → `not_proven` — это и доказательство
эффективности контроля, и защита от ложного «атака не сработала». В memnotsafe
`cross_user_bac_protected.yaml` *обязан* давать success=False — это регресс
контроля, а не баг.

**Перенос:** прогонять матрицу `memrot` в паре режимов цели и репортить дельту
как отдельную метрику качества защиты.

### 2.6 Audit → Attack и маппинг на стандарты (все три)

MOROK и `memrot` роднит идея: статический аудит (`mcp_audit`, `rule_id`
MEM-*/AUTH-*/TOOL-*) **ранжирует** каталог атак. memnotsafe добавляет выходные
форматы под ИБ-процесс: **SARIF**, HTML-воронку, маппинг находок на **MITRE
ATLAS / OWASP ASI**.

**Перенос:** `memrot` уже несёт ATLAS/ASI в `taxonomy.py`; стоит довести
экспорт находок до SARIF, чтобы результаты садились в стандартный ИБ-пайплайн.

## 3. Каталог векторов атаки на память (сводно по трём проектам)

Ниже — объединённый список техник, сгруппированный по таксономии `memrot`.
Колонка «Реализация» указывает, где механика уже воплощена, чтобы её можно было
портировать.

### 3.1 Внедрение инструкции в память (`memory_prompt_injection`, ASI06.1)

| Вектор | Механика | Реализация |
|---|---|---|
| Прямое переопределение правил | «глобальная политика/standing rule» пишется в память как системная директива | memnotsafe `direct_poisoning`; red-alert `memory-poisoning`; MOROK `memory_policy_conformant` |
| Отсроченный триггер («спящий») | правило безобидно до конкретного условия/фразы-активатора | red-alert `memory-poisoning-sleeper` |
| Ложный общий контекст | внушение «мы это уже обсуждали / так делали раньше» | memnotsafe `fake_shared_past`, `false_precedent` |
| Процедурный графт | вредоносный шаг вшивается в легитимную процедуру | memnotsafe `procedural_graft`, `document_regulation_graft` |
| Отмывание согласия | фабрикуется запись о полученном согласии/одобрении | memnotsafe `consent_laundering` |
| Импичмент системного лога | payload маскируется под системную/диагностическую запись | memnotsafe `system_log_impersonation` |

### 3.2 Инъекция через результат инструмента (`tool_output_instruction_injection`, ASI06.1)

| Вектор | Механика | Реализация |
|---|---|---|
| Веб-поиск как канал | инструкция приходит в сниппете результата поиска, не в чате | memrot `generic_tool_websearch_injection`; MOROK-домен `tool_output_web_search_poisoning` |
| Документ / e-mail как канал | payload в теле документа или письма, которое агент читает | memrot `generic_tool_document_injection`, `generic_tool_email_injection` |
| Эхо ошибки инструмента | текст ошибки инструмента трактуется как инструкция | memnotsafe `tool_error_echo_poisoning` |
| Захват аргументов вызова | внедрённое правило меняет **аргументы** будущего вызова (напр. чужой `cus`) | memnotsafe `tool_argument_hijack`; MOROK `bac_tool_argument`, `poison_to_tool_chain` |

### 3.3 Утечка чувствительных данных (`sensitive_data_leakage`, ASI06.2)

| Вектор | Механика | Реализация |
|---|---|---|
| Глобализация приватного факта | приватный факт одного пользователя записывается в общий scope и всплывает у другого | MOROK отчёт «private-fact-globalization» |
| Peer-эксфильтрация | память используется как канал выноса данных другому «пиру» | red-alert `memory-poisoning-peer-exfil` |
| Утечка системного промпта | разведка/вытягивание системной инструкции (потолок `indirect`) | все три: `system-prompt-leak(age)` |

### 3.4 Подмена маркеров доступа (`protected_key_tampering`, ASI06.3)

| Вектор | Механика | Реализация |
|---|---|---|
| Эскалация scope | внедрение записи, повышающей уровень доступа/область | memnotsafe `scope_escalation` |
| Cross-user BAC | обращение за данными другого принципала через память/аргумент | memnotsafe `cross_user_bac`; MOROK BAC 4/4; red-alert `cross-user-portfolio` |
| Подмена контакта/владельца | перезапись «доверенного контакта» или владельца записи | memnotsafe `contact_supersede` |

### 3.5 Нарушение целостности памяти (`memory_integrity_violation`, ASI06.4)

| Вектор | Механика | Реализация |
|---|---|---|
| Тихая перезапись факта | легитимный факт молча заменяется без проверки происхождения | memrot `generic_memory_integrity_violation` |
| Cross-topic smuggle | payload протаскивается под видом смены темы | memnotsafe `cross_topic_smuggle` |

### 3.6 Аномалия объёмного впрыска (`bulk_injection_anomaly`, ASI06.5)

| Вектор | Механика | Реализация |
|---|---|---|
| Объёмный/повторяющийся впрыск | крупная запись повышает шанс пережить суммаризацию памяти | memrot `generic_bulk_injection_anomaly` |
| Длинный отвлекающий префикс | payload прячется за длинным «шумовым» текстом | red-alert `ryan-gosling-bladerunner-speech` |

### 3.7 Каналы обхода фильтров (техники доставки, `ATTACK_TECHNIQUE_CATEGORIES`)

Это ортогональная ось — **как** доставляется любой из payload'ов выше:

| Техника | Механика | Реализация |
|---|---|---|
| Authority / compliance impersonation | payload «от администратора/аудитора» | memrot `authority_impersonation` |
| Obfuscation / encoding | base64 / rot13 / hex / unicode-escape вокруг инструкции | memrot `obfuscation_encoding`; red-alert `base64-injection` |
| Payload splitting | сборка из нескольких безобидных фрагментов | memrot `payload_splitting` |
| Many-shot priming | длинный фейковый диалог легитимизирует правило | memrot `many_shot` |
| Low-resource / cross-lingual | тот же payload на менее фильтруемом языке | memrot `low_resource_language`; memnotsafe `cross_lingual_insertion` |
| Refusal / roleplay / context-ignore | подавление отказа, персона, «игнорируй контекст» | memrot `refusal_suppression`, `roleplay_persona`, `context_ignore` |
| Импортированные банки джейлбрейков | garak DAN, TrustAIRLab | memrot `catalog/imported/*` |
| **Мультимодальная инъекция** | инструкция в изображении (портфель/скрин), которое агент разбирает | red-alert `*-image-injection` |
| Goal hijack через сторонний инструмент | перехват цели через внешний агент/инструмент | red-alert `openclaw-goal-hijack` |

## 4. Чего у нас пока нет — приоритетный список расширения `memrot`

Отсортировано по соотношению «эффект / стоимость внедрения».

1. **Лестница oracle'ов по строгости эффекта** (из memnotsafe):
   `persist < retrieve < adopt < tool-effect < external-effect`. Даёт честную
   градацию CONFIRMED вместо бинарного «сработало/нет».
2. **Мультимодальный канал доставки** (из red-alert): инъекция в изображении —
   у `memrot` есть текстовые каналы (web/doc/email), но нет image-vector.
3. **Отсроченный триггер / «спящий» payload** (из red-alert): проверка, что
   правило активируется по условию, а не сразу — прямой тест на суммаризацию и
   долговечность памяти.
4. **Семейства «социальной» инъекции** (из memnotsafe): `fake_shared_past`,
   `consent_laundering`, `false_precedent`, `system_log_impersonation` — их нет
   в текущем generic-каталоге, а они дают низкосигнальные, трудноловимые атаки.
5. **Экспорт SARIF** (из memnotsafe): посадить находки в стандартный
   ИБ-пайплайн; ATLAS/ASI-маппинг для этого уже есть в `taxonomy.py`.
6. **Brief-режим автономного атакующего** (из MOROK): фиксируем только цель +
   предикат, порядок ходов отдаём адаптивному атакующему поверх нашего
   `--adaptive`.
7. **A/B `vulnerable`/`protected`** как штатная метрика (из MOROK/memnotsafe):
   дельта между режимами цели = измеримое качество защиты, плюс страховка от
   ложного «атака не сработала».

## 5. Инварианты, которые все трое соблюдают (и нам стоит держать)

- **Успех ≠ текст ответа.** Текстовый сигнал — потолок `indirect`/`UNOBSERVABLE`,
  никогда полный «confirmed».
- **Ошибочные попытки — вне знаменателя ASR.** Техническая ошибка (`ERROR`) не
  маскируется под «атака не сработала» (`CLEAN`).
- **Target-специфика — только в профиле/каталоге-оверлее**, ядро о цели не знает
  (у `memrot` — `profiles/` + `catalog/prompts/domain/<name>/`; у MOROK инвариант
  защищён тестом `test_no_target_leak.py`).
- **Артефакты прогона иммутабельны**, регрессия создаёт новые каталоги.
- **Только авторизованное тестирование**, изолированный стенд, синтетические
  данные.
