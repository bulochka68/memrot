# 3. MVP, критерии успеха, вклад AI Product, риски и шаг к пилоту

Материал 3 из 3 продуктового комплекта. Финальная версия, AI Product Hack 2026.

---

## 3.1. Границы реализованного MVP

**Что вошло** (всё перечисленное работает на закоммиченных данных, без внешних сервисов):

| Блок | Содержание |
|---|---|
| Статический аудит `mcp_audit` | 28 контролей (MEM-01…10, AUTH-01…06, INFRA-01…03, TOOL-01…05, EGRESS-01…02, INV-01…02), отчёт схемы `agent-security-audit 2.0` с `claim_status`, покрытием и индикатором lethal trifecta; 5 режимов (offline / live-inventory / trace-review / controlled-validation / baseline-comparison); `lint-profile`, `baseline`, `drift`, `migrate`, `validate` |
| Харнесс атак `memrot` | Каталог 77 вариантов (39 нейтральных + 26 overlay инвест-банка + 12 overlay MemPalace), 5 адаптеров (`openai_compat`, `http_generic`, `mcp_client`, `genai_invest`, `callable`), 5 вердиктов, ASR в 7 разрезах, лестница `path_state`, HTML-отчёт, JSONL-трасса |
| Связка аудит → атака | `--audit --audit-mode {filter,prioritize,ranked}`, `pipeline.audit_then_attack`, общий словарь `rule_id` / `path_state` |
| Опциональные усилители | LLM-судья, LLM-мутации промптов, адаптивный атакующий (PAIR/TAP-lite), импорт банков джейлбрейков как отдельной оси угроз |
| Портируемость | Профиль системы + оверлей каталога; перенос на чужую систему (MemPalace) без правок движка |
| Гейт в CI | Exit-коды `0/1/2/3/4` у аудита, `--gate` у харнесса атак |

**Что сознательно не вошло** (и почему — гипотезы H3/H4/H6):

- Веб-интерфейс, сервис, история прогонов, мультипользовательский режим → H6.
- Единый security score / «процент безопасности» → H3.
- Автопочинка находок и генерация патчей — продукт даёт основание для решения, не принимает его.
- Runtime-мониторинг в проде: продукт предрелизный, не SOC-инструмент.
- Не-memory-агенты (чистый RAG, классификаторы) — вне валидированной области.
- Пакет в PyPI, установка, версионирование релиза — запускается из клона.

## 3.2. Основной пользовательский сценарий (сквозной)

Один сквозной путь, который работает целиком, — от «у меня есть агент» до «у меня есть
основание для решения»:

```
1. ОПИСАТЬ СИСТЕМУ          python -m mcp_audit lint-profile profiles/<my>.json --root <src>
   → «18/28 правил открываются на доступных источниках; чего не хватает — вот список»
   (карта пробелов ДО аудита, а не стена not_evaluated после)

2. ПРОАУДИТЬ                python -m mcp_audit audit <manifest>.json --json stand.json --md report.md
   → 26 подтверждённых находок, 4 гипотезы, покрытие 21/26, exit-код для CI

3. АТАКОВАТЬ ПО ПРИОРИТЕТУ  python -m memrot run --config <attack>.json --audit stand.json \
                              --audit-mode ranked --out .attack --report-html .attack/run.html
   → сводка аудита печатается ПЕРВОЙ и переупорядочивает каталог;
     на каждую попытку — один из 5 вердиктов

4. ПРОЧИТАТЬ РЕЗУЛЬТАТ      .attack/run.json + run.html + JSONL-трасса
   → ASR с честным знаменателем; path_state поднимает статус находки
     со static_path_supported до runtime_path_observed / control_violation_observed

5. ПОСТАВИТЬ ГЕЙТ           --gate  → exit 1 на CONFIRMED, exit 2 на неполное покрытие
```

Шаг 5 — это то, ради чего сценарий заканчивается именно так: продукт должен встать
в пайплайн релиза, иначе он не влияет на решение (см. H6).

## 3.3. Критерии успеха и результаты их проверки

Способ проверки — прогон на закоммиченных снапшотах и детерминированных фикстурах;
все команды воспроизводимы из клона репозитория.

| # | Критерий успеха | Способ проверки | Результат |
|---|---|---|---|
| К1 | Аудит воспроизводимо находит дефекты на реальной системе | `mcp_audit audit examples/genai_invest_stand.manifest.json` | ✅ 26 подтверждённых находок (8 CRITICAL / 12 HIGH / 6 MEDIUM), 4 гипотезы; контроли PASS 5 / FAIL 16 / INCONCLUSIVE 3 / N/A 2 / NOT_EVALUATED 2 |
| К2 | Отчёт не выдаёт покрытие за безопасность | тот же прогон | ✅ `mandatory_control_coverage` 21/26 (80.8%), **runtime 0/26 (0.0%)**, 5 неразрешённых контролей названы поимённо; поля `score` в схеме нет |
| К3 | Успех атаки измеряется состоянием, а не текстом ответа | `audit_then_attack`, нейтральный пул, top-8, детерминированная уязвимая фикстура | ✅ 8/8 CONFIRMED; **3 из них `control_violation_observed`** — payload дошёл до другого принципала |
| К4 | Косвенный вектор (результат инструмента) работает | `run_matrix`, вариант web-search-инъекции | ✅ CONFIRMED, `laundering_detected=True`, `delivery_channel=tool_result` |
| К5 | Движок переносится на чужую систему данными | аудит MemPalace + `tests/test_mempalace_attack.py` | ✅ 11 находок (3 CRITICAL / 7 HIGH / 1 MEDIUM) на 45 инструментах; правок движка нет; профиль открывает 18/28 правил |
| К6 | Поведение закреплено регрессией | `pytest` | 🟡 320 passed, 3 skipped — **но 2 модуля не собираются** (см. 3.6) |
| К7 | Время до обоснованного решения о релизе сокращается | — | ❌ **не проверено**: baseline у носителя проблемы не снят, интервью не проводились. Главный RAT пилота |

**Итог:** 5 критериев из 7 подтверждены прогоном, 1 подтверждён с дефектом, 1 не проверен.
Непроверенный — самый важный для коммерческой части, и мы это не маскируем.

## 3.4. Журнал принятых решений

| # | Решение | Почему | Что изменилось в реализации |
|---|---|---|---|
| Р1 | Никакого единого security score | Нет честного знаменателя (H3) | В схеме отчёта нет `verified`/`score`; вместо них `claim_status` на каждое утверждение + поимённое покрытие |
| Р2 | Пять вердиктов вместо pass/fail | Неполный прогон ≠ чистый прогон | `ERROR`/`INVALID`/`NOT_EVALUATED` исключены из знаменателя ASR; пустая категория печатается `n/a (0/0)`, а не 0% |
| Р3 | Аудит и атака — два независимых пакета | Портируемость и независимая эволюция | `memrot` **не импортирует** `mcp_audit` (проверяемо грепом); связь только строками `rule_id` / `path_state` и JSON-отчётом |
| Р4 | Ядро — stdlib-only, LLM опциональны | Прогон не должен требовать ключа и не должен быть недетерминированным (H8) | Black-box путь на `urllib`; LLM-судья деградирует к литеральному детектору при отказе |
| Р5 | CLI + JSON + статический HTML вместо сервиса | Пользователь живёт в CI и терминале (H6) | `emit_html` даёт самодостаточный файл; серверного контура нет |
| Р6 | Привязка к системе — только данными | Кейсодатель как первый сегмент, а не единственный (H5) | Профиль + оверлей каталога; перенос на MemPalace без правок движка |
| Р7 | Карта пробелов печатается до аудита | «Просто запусти сканер» не работает (H4) | Команда `lint-profile`: схема, пути, символы, регулярки, ссылки на правила + «сколько правил открывается» |
| Р8 | Сводка аудита печатается перед таблицей атак | Приоритет задаёт аудит, а не наоборот (H2) | Порядок вывода в CLI — не косметика, а утверждение о методологии |
| Р9 | Секреты только через окружение | Конфиги коммитятся и переносятся | В конфиге только `credential_ref` → `MEMROT_CRED_<ref>` |
| Р10 | Джейлбрейк-банки — отдельная ось ASR | Разные утверждения о системе нельзя складывать (H7) | `threat_model=llm_jailbreak_susceptibility` считается отдельно от отравления памяти |

## 3.5. Вклад AI Product: как продуктовые решения изменили техническую реализацию

Это ключевой раздел комплекта. Ниже — не «мы обсудили», а конкретные места, где
**продуктовое решение поменяло код**, и что было бы, если бы решение приняли иначе.

| Продуктовое решение | Техническое следствие | Место в коде | Что было бы без него |
|---|---|---|---|
| Отказ от единого score (H3) | Вся модель данных отчёта построена вокруг утверждения с источником и статусом, а не вокруг числа | схема `agent-security-audit-2.0`, `claim_status`, `coverage` | Красивое демо-число, за которым нельзя защитить релиз |
| «Неполный прогон ≠ чистый» (Р2) | Пять вердиктов + отдельный знаменатель ASR + `n/a (0/0)` | `memrot/runner/verdict.py`, `memrot/reporting/aggregate.py` | Тихие 0% на категориях, которые никто не смог проверить |
| Статика не доказывает (H10) | Лестница `path_state` как общий контракт двух подсистем | `memrot/models.py::path_state_for`, `claim_status` в аудите | Находки аудита выдавались бы за подтверждённые атаки |
| Аудит задаёт приоритет атаки (H2) | Ранжирование каталога по серьёзности находок + печать ограничений ранжирования | `memrot/audit_plan.py`, `memrot/pipeline.py` | Равномерный перебор банка промптов вместо целевой проверки |
| Кейсодатель — первый сегмент (H5) | Запрет на импорт `mcp_audit` из `memrot`; вся привязка — в данных | границы пакетов, `profiles/`, `catalog/prompts/domain/` | Инструмент под одну систему, не переживающий Demo Day |
| «Сканер из коробки» не работает (H4) | Отдельная команда линта профиля с картой пробелов | `mcp_audit/validation/profile.py` | Стена `not_evaluated`, неотличимая от «всё в порядке» |
| Пользователь живёт в CI (H1, H6) | Exit-коды как продуктовый интерфейс: 0/1/2/3/4 у аудита, `--gate` у атак | `mcp_audit/cli.py`, `memrot/cli.py::_exit_code` | Отчёт, который читают глазами и не встраивают в релиз |
| LLM — опция, не ядро (H8) | Ядро stdlib-only; судья с деградацией | `memrot/detectors/` | Обязательный API-ключ и недетерминированный вердикт |

**Обратное направление тоже было:** техническое наблюдение меняло продуктовую рамку.
Цифра `runtime 0/26` из первого же прогона аудита — это то, что убило H10 и, как следствие,
породило центральную связку продукта «аудит → приоритет → атака → повышение статуса».

**Как ИИ использовался в самой работе.** Разработка велась в связке «люди + ИИ»:
из 51 коммита в истории репозитория 19 сделаны агентом Claude Code, остальные — участниками
команды; ИИ применялся для генерации каркаса каталога атак, обвязки тестов и черновиков
документации, разбор и решения по методологии (вердикты, покрытие, лестница `path_state`)
принимались людьми. Проверка каждой сгенерированной цифры прогоном — часть процесса:
все числа в этом комплекте получены запуском, а не пересказом.

## 3.6. Риски и ограничения AI-решения

**Методологические (внутренние для продукта):**

1. **Статика ≠ поведение.** 26 находок статически подтверждены, 0 — рантайм-подтверждены.
   Отчёт говорит об этом прямо; но пользователь, читающий по диагонали, может принять
   `CRITICAL` за «эксплуатируется».
2. **`CLEAN` — не доказательство безопасности.** Это «не воспроизведено в этом прогоне
   на этом каталоге». Легенда печатается в каждом прогоне именно поэтому.
3. **Литеральный детектор ловит маркер, а не смысл.** Перефразированная закладка без
   канарейки даст ложноотрицательный результат. Опциональный LLM-судья закрывает это
   ценой недетерминизма.
4. **ASR зависит от каталога.** 77 вариантов — не покрытие поверхности атак.
   Сравнивать ASR двух систем корректно только на одном и том же каталоге и прогоне.
5. **Недетерминизм цели.** Тот же вариант против той же LLM может дать разный вердикт
   между прогонами; единичный `CONFIRMED` — сигнал, единичный `CLEAN` — нет.

**Ограничения данных и области применимости:**

6. **n=1 чужая система.** Портируемость доказана на MemPalace; обе валидированные цели —
   memory-центричные агенты. Про RAG-only и не-агентные системы утверждений не делаем.
7. **Живых интервью не было.** Вся продуктовая часть опирается на артефакты и две системы,
   не на внешний сигнал от носителей проблемы. Это признанный долг (H1, К7).
8. **Порядок величины рынка не измерялся** и в материалах не заявляется.

**Ответственность и двойное назначение:**

9. Инструмент атакующий по своей природе. Он предназначен для **авторизованной**
   проверки собственных систем: секреты не хранятся в конфигах (только `credential_ref`),
   режим `controlled-validation` работает только на изолированных фикстурах с
   зарегистрированными кейсами, а `MCP_AUDIT_SANDBOX` требует явного включения.
10. Отчёты содержат находки безопасности по конкретной сборке — их распространение
    вне команды владельца системы требует отдельного решения.

**Эксплуатационные дефекты на день сдачи (честный список):**

11. **`memrot/ui.py` отсутствует в репозитории**, хотя `memrot/cli.py` его импортирует →
    `python -m memrot --help` и любой запуск CLI падают с `ImportError` на свежем клоне;
    два тестовых модуля (`test_attack_cli.py`, `test_attack_catalog_taxonomy_strict.py`)
    не собираются по той же причине. Движок при этом работоспособен: программный путь
    (`pipeline.audit_then_attack`, `run_matrix`) и весь `mcp_audit` работают, остальные
    320 тестов проходят. **Блокер №1 к пилоту.**
12. **`examples/notebooks/memrot_full_demo.ipynb` отсутствует**, хотя README на него ссылается.
13. В `memrot_quickstart.ipynb` ячейка 3 падает: `build_adapter(FakeVulnerableMemoryApp(), …,
    with_tool_staging=True)` требует `stage_tool_response`, которого у этой фикстуры нет
    (он есть у `FakeToolPoisonableApp`).
14. README описывает клонирование в каталог `aith_redteaming`, тогда как репозиторий
    называется `memrot`.

Пункты 11–14 — следствие финальной пересборки демо в последний день. Все они
воспроизводятся одной командой и чинятся до пилота (шаг 0 ниже).

## 3.7. Выводы по результатам хакатона

1. **Гипотеза о классе проблемы подтвердилась.** Атака на память и инструментальный
   контур измерима состоянием, и эта проверка находит то, чего однохододовые сканеры
   не видят: 3 из 8 подтверждённых атак дошли до другого принципала.
2. **Главная методологическая ставка — честный знаменатель — оказалась дороже,
   чем красивая метрика, и мы её сделали.** Отказ от единого score (H3) стоил нам
   демонстрационного числа и переписал схему отчёта, но именно он делает результат
   защищаемым перед безопасностью.
3. **Пять гипотез из десяти опровергнуты, и каждая изменила продукт**, а не только
   формулировку: H3 → схема отчёта, H4 → команда `lint-profile`, H6 → границы MVP,
   H8 → stdlib-only ядро, H10 → лестница `path_state` и вся связка «аудит → атака».
4. **Портируемость доказана на чужой системе**, но ровно на одной; обобщать рано.
5. **Продуктовая часть отстаёт от технической.** Мы построили инструмент, который
   технически делает правильную вещь, но не проверили ценность на живом носителе
   проблемы. Это осознанный, названный вслух долг, а не оптимистичное умолчание.

## 3.8. Следующий шаг к пилоту

**Шаг 0 — гигиена (до пилота, 1–2 дня).** Восстановить `memrot/ui.py` и недостающий
ноутбук, починить ячейку квикстарта, привести README к имени репозитория; критерий
готовности — `pytest -q` зелёный **без исключений** и `python -m memrot --help`
работает на свежем клоне. Пункты 11–14 раздела 3.6 закрыты.

**Шаг 1 — снять baseline (неделя 1).** 3–5 разговоров с носителями проблемы
(инженеры, выпускающие агентов с памятью): как сегодня отвечают на вопрос «безопасен ли он»,
сколько это стоит в часах, что считают сейчас. Цель — проверить RAT (К7) и получить
единицы измерения ценности, которых у нас пока нет.

**Шаг 2 — пилот на одной реальной системе заказчика (недели 2–4).**
Grey-box, полный сквозной сценарий: профиль → `lint-profile` → аудит → ranked-атака → отчёт → гейт.
**Критерии успеха пилота, зафиксированные заранее:**

| Критерий | Порог |
|---|---|
| Хотя бы одна находка поднята со `static_path_supported` до `runtime_path_observed` | ≥ 1 |
| Профиль системы открывает разумную долю правил | ≥ 18/28 |
| Время от «есть доступ к системе» до первого отчёта | ≤ 1 рабочий день |
| Гейт встал в CI заказчика и не даёт ложных срабатываний на зелёной сборке | 0 ложных блокировок за 2 недели |
| Инженер заказчика самостоятельно повторяет прогон по документации | без нашей помощи |

**Шаг 3 — обобщение (после пилота).** Библиотека готовых профилей под типовые стеки
(LangGraph, mem0, MCP-хабы) — та самая механика FDE «кастомная работа у одного клиента
становится фичей продукта для всех». Плюс упаковка в устанавливаемый пакет и
runtime-подтверждение находок (закрытие `runtime 0/26`) как следующая методологическая цель.
